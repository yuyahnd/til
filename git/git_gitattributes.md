# gitattributes 
gitattributes - Defining attributes per path

# SYNOPSIS
 $GIT_DIR/info/attributes, .gitattributes

# DESCRIPTION
gitattributesファイルは、パス名に属性を割り当てる単純なテキストファイルです。
gitattributes ファイルの各行は、次の形式になっています。

```
pattern attr1 attr2 ...
```

つまり、パターンと属性リストを空白で区切った形式です。行頭や行末の空白は無視されます。# で始まる行は無視されます。二重引用符で始まるパターンは、C言語形式で引用符付きとして扱われます。パターンが対象のパスに一致する場合、その行に記載された属性がそのパスに適用されます。

特定のパスにおいて、各属性は以下のいずれかの状態をとることができます。

* Set
そのパスは、特殊な値「true」を持つ属性を有しています。これは、属性リストにその属性名のみを記述することで指定されます。

* Unset
そのパスは、特殊な値「false」を持つ属性を有しています。これは、属性リストにおいて、属性名の前にダッシュ（-）を付加して記述することで指定されます。

* Set to a value
そのパスは、指定された文字列値を伴う属性を持っています。これは、属性リストにおいて、属性名を記述し、続けて等号（=）と値を記述することで指定されます。

* Unspecified
パスに一致するパターンがなく、かつそのパスが当該属性を持つか否かを示すものもない場合、そのパスの属性は「未指定（Unspecified）」であるとみなされます。


パスに複数のパターンが一致する場合、後の行が前の行を上書きします。この上書きは属性ごとに行われます。
パターンがパスに一致するかどうかを判断する規則は、いくつかの例外を除き、.gitignoreファイルの場合と同じです（gitignoreを参照）。

* 否定的なパターンは禁止されています。

* ディレクトリに一致するパターンは、そのディレクトリ内のパスには再帰的に一致しません（したがって、attributesファイルで末尾にスラッシュを付けた `path/` という構文を使用しても意味がありません。代わりに `path/**` を使用してください）。

パスにどの属性を割り当てるかを決定する際、Gitはまず `$GIT_DIR/info/attributes` ファイル（これが最も高い優先順位を持ちます）を参照し、次に当該パスと同じディレクトリにある `.gitattributes` ファイル、およびその親ディレクトリから作業ツリーのトップレベルに至るまでの各ディレクトリにある `.gitattributes` ファイルを参照します（`.gitattributes` を含むディレクトリが当該パスから離れているほど、その優先順位は低くなります）。最後に、グローバルおよびシステム全体の設定ファイルが考慮されます（これらは最も低い優先順位を持ちます）

ワーキングツリーに .gitattributes ファイルが存在しない場合、インデックス内のパスがフォールバックとして使用されます。チェックアウトの際には、まずインデックス内の .gitattributes が使用され、それが存在しない場合はワーキングツリー内のファイルがフォールバックとして使用されます。

特定の1つのリポジトリだけに属性を適用したい場合（例えば、そのリポジトリにおける特定のユーザーのワークフローに固有のファイルに属性を割り当てる場合など）は、`$GIT_DIR/info/attributes` ファイルに属性を記述します。一方、バージョン管理の対象とし、他のリポジトリにも配布すべき属性（つまり、すべてのユーザーに関係する属性）については、`.gitattributes` ファイルに記述します。単一ユーザーのすべてのリポジトリに適用すべき属性は、`core.attributesFile` 設定オプションで指定されたファイルに記述します（git-config[1] を参照）。このオプションのデフォルト値は `$XDG_CONFIG_HOME/git/attributes` です。`$XDG_CONFIG_HOME` が未設定または空の場合は、代わりに `$HOME/.config/git/attributes` が使用されます。システム上のすべてのユーザーに適用する属性は、`$(prefix)/etc/gitattributes` ファイルに記述します。

パスの属性設定を「未指定（Unspecified）」状態に上書きする必要がある場合があります。これを行うには、属性名の先頭に感嘆符（!）を付けます。

# RESERVED BUILTIN_* ATTRIBUTES
`builtin_*` は、組み込み属性値のために予約された名前空間です。この名前空間配下でユーザーが定義した属性は無視され、警告が生成されます。

* builtin_objectmode
この属性は、ファイルのビットモード（40000、120000、160000、100755、100644）に基づいてファイルをフィルタリングするためのものです（例: `(attr:builtin_objectmode=160000)`）。これらの値は、`git check-attr builtin_objectmode -- <file>` コマンドで確認することもできます。オブジェクトがインデックスに含まれていない場合、`git check-attr --cached` は `unspecified` を返します。

# EFFECTS
パスに特定の属性を割り当てることで、Gitの特定の動作に影響を与えることができます。現在、以下の操作が属性を考慮するようになっています。

* Checking-out and checking-in
これらの属性は、`git switch`、`git checkout`、`git merge` などのコマンドが実行される際、リポジトリに格納されているコンテンツがワーキングツリーのファイルにどのようにコピーされるかに影響します。また、`git add` や `git commit` を行う際に、ワーキングツリーで用意したコンテンツがリポジトリにどのように格納されるかにも影響を及ぼします。

* text
この属性は、対象のパスをテキストファイルとして指定するもので、これにより改行コードの変換が可能になります。該当するファイルがインデックスに追加される際、そのファイルの改行コードはインデックス内で LF に正規化されます。逆に、インデックスから作業ディレクトリへファイルがコピーされる際は、`eol` 属性、Git の設定、およびプラットフォームに応じて、改行コードが LF から CRLF に変換される場合があります（`eol` 属性に関する説明を後述の項目で参照してください）。

* Set
パスに対して text 属性を設定すると、前述の通り、チェックインおよびチェックアウト時の改行コード変換が有効になります。たとえ以前に CRLF の改行コードで Git に追加されたファイルであっても、チェックインのたびに、インデックス内では改行コードが LF に正規化されます。
